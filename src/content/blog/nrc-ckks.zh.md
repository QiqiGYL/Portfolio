# 我扫了 76 万组 CKKS 参数，就为了回答“精度到底够不够”

*2024 年秋 — National Research Council Canada，Software Developer co-op*

**30 秒科普。** 全同态加密（FHE）让你可以在*不解密*的情况下对数据做计算——你把加密后的表格交给别人，他们在密文上跑计算，还你一个加密的答案，解密出来就是正确结果，而他们全程看不到你的数据。我用的开源库 OpenFHE 实现了好几种 FHE 方案：BFV 和 BGV 做精确整数运算，**CKKS** 做近似数运算（想想小数、机器学习、统计）。我们组的目标就是 CKKS，下面所有内容都是关于它的。

2024 年秋我在加拿大国家研究院（NRC）做开发 co-op，是整个组里唯一的 programmer，队友全是搞隐私计算研究的 PhD。他们用的是 CKKS——一种支持近似数运算的同态加密方案，实现基于 [OpenFHE](https://github.com/openfheorg/openfhe-development) 库。用 CKKS 跑任何东西之前，都得先定一组参数：安全级别 $\lambda$、ring dimension $N$、scaling modulus $\Delta$、first modulus $q_0$、乘法深度 $L$、目标精度。理论上有公式，能算出某组参数“应该”给出多少精度。但研究员们想知道的是：**实际上**到底有多少——横跨几十万种组合，每一组都实测一遍的那种知道。

于是我把整套机器造了出来：C++ 扩展、测量流水线、数据库、GUI、benchmark，全是我写的。

## 第一部分：C++ 贡献

### 随机密文生成

做 benchmark 得有像样的测试输入：在*指定*乘法层级上的密文。OpenFHE 原生没提供顺手的办法，所以我写了一个 C++ 小扩展，直接插进 OpenFHE 的 encoding 模块。给它密钥对、明文范围和目标层级，它就生成该层级上的随机密文。整个流水线里所有测量程序都用它。

### 密文求逆：Newton vs Goldschmidt

同态加密里没有除法——你没法直接拿两个密文相除。所以我实现了两种经典的迭代算法，在*加密*数据上算 $1/b$：

- **Newton 法**：$z \leftarrow z(2 - bz)$，二次收敛。
- **Goldschmidt 法**：并行友好的变体，往 $1$ 缩放。

都在我写的求逆模块里，外加一个小辅助函数（把输入归一化到 Goldschmidt 要求的 $(0, 2)$ 区间），以及一个演示用法的示例程序。有个我很喜欢的调试细节：开发的时候我每轮迭代都把中间值解密出来打印，亲眼看着近似值收敛——毕竟密文里面长啥样你是看不见的。

## 第二部分：76 万组参数的精度大扫描

### 生成参数表

Python 脚本先算出 CKKS 参数之间的理论关系，写出完整网格：一张各安全级别可行范围的边界表，外加完整的大参数表——$(\lambda, \log_2 N, \log_2 \Delta, q_0, L)$ 的所有组合，每组附带理论 $\log_2$ 精度。

### 一行一行地测出真相

对每一行，一个 C++ 测量程序按参数建出对应的 OpenFHE 加密上下文，在乘法深度内的每个层级组合上生成随机密文、做乘法、解密，用库自带的精度读数记录实测精度。shell 脚本一次只喂一行，C++ 二进制一次只吃一行参数。

这个“一次一行”不是最初的设计——它是被逼出来的。第一版我想把多行 batch 进一个 `CryptoContext` 里跑，结果 context 把内存吃光，进程直接暴毙。于是我放弃了 batching：shell 驱动逐行喂，测完立即释放内存，之后扫描连续跑了约两周。我也做了同一套测量程序的 SQLite 输入版，这样可以从数据库断点续跑，而不用反复解析百万行 CSV——契约还是一次一行，只是换了输入源。顺带一提，我们其实同时还在跑一个更广的扫描——$156{,}985$ 行，覆盖安全级别 $128$、$196$、$256$、$\log_2 N$ 从 $14$ 到 $17$——但两周过去了它还没跑完，所以研究先收敛到已完成的 $\lambda = 128$ 数据集上：$760{,}647$ 行实测数据，覆盖 ring dimension $\log_2 N = 14$、$15$、$16$。

### 从 CSV 到研究员真正能用的工具

一百万行的 CSV 研究员是不会去 grep 的，所以我把原始产出变成了真正能用的东西：

- 一个 Python 脚本把结果转成 SQLite 数据库。
- 一个过滤步骤：对每组唯一参数组合保留**最小**实测 OpenFHE 精度（你真正敢拿去用的那个保守数字）。
- 一个 Tkinter 图形界面（v2）：研究员选 $\lambda$、$L$ 和目标精度后，它会**并行走两条路径**——理论 `log2_precision` 与实测 `OpenFHE_precision`——再级联筛到成本最低的可行 $(N, \Delta, q_0)$。这些结果后来被拿去写论文。

## 第三部分：数据说了什么

### 实测精度几乎全面碾压理论

![CKKS 精度：实测 vs 理论](/blog/nrc-ckks/assets/precision-deviation.png)

$\lambda = 128$ 下全部 $760{,}647$ 组参数：

- **$98.8\%$** 的组合里，OpenFHE 实测精度**高于**理论公式的预测。
- 中位数差距：**$+7$ bits**；均值 **$+6.2$ bits**（标准差 $1.8$）。
- 把理论精度对上实测精度，结论一眼就出来——几乎整片点云都在 $y = x$ **上方**：

![理论精度 vs 实测精度](/blog/nrc-ckks/assets/precision-theory-vs-measured.png)

理论精度公式偏保守。只按理论选参数的研究员，大概要么浪费了约 $6$ bits 精度，要么把参数配得过于富余。有了实测表，他们可以直接用经验验证过的数字。

### Benchmark：乘法的成本几乎全花在重线性化上

用 Google Benchmark（每个 case 跑 $20$ 次迭代，扫遍深度 $L$ 内的所有密文层级组合），我测了 $8$ 个核心 CKKS 操作，共 $1{,}390$ 次 benchmark：

![CKKS benchmark：各操作耗时中位数](/blog/nrc-ckks/assets/benchmark-timings.png)

- 密文×密文乘法：中位数约 **$52\,\mathrm{ms}$**。
- 同样的乘法*不带*重线性化（`EvalMultNoRelin`）：约 **$3.4\,\mathrm{ms}$**——快了**约 $15\times$**。
- 加减法：约 $1.3$–$1.9\,\mathrm{ms}$；密文×明文操作：亚毫秒级。

结论很直白：重线性化吃掉了乘法的大部分成本。这是个可以直接引用的设计权衡——如果你的电路能接受乘法后更大的密文，跳过重线性化就能换来一个数量级的加速。

## 我带走了什么

进去的时候我是个写过一点 C++ 的数学本科生，出来的时候我：

- **给一个真正的密码学库写过扩展**——随机密文生成和两种求逆算法，直接写在 OpenFHE 的内部结构上（DCRTPoly、RNS-CKKS context、key switching）。
- **造过一条无人值守跑两周的数据流水线**——Python 表生成 → C++ 实测 → SQLite → Tkinter GUI，一百多万条记录。
- **解决过一个真实的系统级问题**——密码学 context 的内存爆炸，靠重新设计数据流（逐行+即时释放）解决，而不是加机器。
- **交付过 PhD 研究员真的在用的工具**——那个 GUI 把 76 万行的数据库变成了非程序员几秒钟就能查的东西。
